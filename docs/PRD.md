# 모임 이벤트 관리 웹 MVP — PRD

> 버전: v0.1 (초안) · 작성일: 2026-10-23
> 기술 스택: Next.js 16 (App Router) + Supabase (Auth, Postgres, RLS) + shadcn/ui + Tailwind CSS v3

---

## 1. 개요

### 1.1 문제 정의

수영·헬스·러닝 같은 **정기 운동 모임**의 주최자(총무)는 매 회차마다 아래 일을 카카오톡 단체방에서 수작업으로 처리한다.

- 일시·장소 공지를 올리지만 대화에 묻혀 다시 찾기 어렵다.
- "참석합니다" 메시지를 일일이 세어 인원을 집계한다.
- 정원이 있는 모임(레인, 코트, 수업)은 초과·취소·대기 관리가 번거롭다.
- 매주 비슷한 내용을 반복해서 새로 작성한다.

### 1.2 비전 / 한 줄 가치 제안

> **"링크 하나로 공지하고, 클릭 한 번으로 참석 현황이 정리되는 모임 관리."**

### 1.3 MVP 목표

가장 빈도가 높고 고통이 큰 **"공지 + 참석 응답 관리"** 만 해결한다. 카풀과 정산은 MVP 이후 단계로 미룬다.

| ---- | ----------------------------------- | --------------------------------------------- |
| 예시 | 30대 직장인, 주 2회 수영 모임 운영  | 모임 회원 8~20명                              |
| 목표 | 공지·집계에 쓰는 시간을 줄이고 싶다 | 일정을 쉽게 확인하고 빠르게 응답하고 싶다     |

| 환경 | 모바일 위주, 가끔 PC                | 거의 100% 모바일                              |

## 3. 핵심 사용자 시나리오

### 3.1 주최자

1. 로그인 후 `이벤트 만들기`에서 제목·일시·장소·설명·정원을 입력한다.
2. 생성 완료 화면에서 **공유 링크를 복사**해 카톡방에 붙여 넣는다.
3. 상세 화면에서 참석/불참/미정/대기자 현황을 실시간으로 확인한다.
4. 다음 회차는 `복제`로 날짜만 바꿔 새로 만든다.

### 3.2 참여자

1. 카톡방에서 링크를 탭한다.
2. 비로그인 상태면 로그인/가입 후 **원래 이벤트 화면으로 복귀**한다.
3. `참석 / 불참 / 미정` 중 하나를 선택한다. 정원이 가득 찼으면 자동으로 대기자가 된다.
4. 응답은 마감 전까지 언제든 변경할 수 있다.

## 4. MVP 범위

| 구분   | 포함 (In)                                                                       | 제외 (Out, 추후)       |
| ------ | ------------------------------------------------------------------------------- | ---------------------- |
| 인증   | 이메일 로그인/가입 (기존 Supabase Auth), 소셜 로그인 (Google·Kakao)             | 네이버 로그인 (4차)    |
| 이벤트 | 생성·조회·수정·삭제, 공유 링크, 복제, 커버 이미지 (1장, 5MB 이하 jpeg·png·webp) | 자동 반복 일정 규칙    |
| 관리자 | 통계 대시보드, 이벤트 관리(숨김·해제), 사용자 관리(역할 변경), 신고 처리        | 감사 로그, 사용자 정지 |
| 참여   | 참석/불참/미정 응답, 정원, 대기자                                               | 초대 코드, 비회원 참여 |
| 알림   | 앱 내 상태 표시, 링크 공유                                                      | 푸시·이메일·카톡 알림  |
| 카풀   | —                                                                               | **카풀 매칭 (2차)**    |
| 정산   | —                                                                               | **비용 정산 (3차)**    |
| 조직   | 이벤트 단위 관리                                                                | 모임(Group)·멤버 풀    |

### 가정 (이견 시 조정)

- 반복 일정은 자동 규칙 대신 **복제 기능**으로 대체한다.
- 모임(Group) 개념 없이 **이벤트 단위**로 시작하며, 주최자는 이벤트 생성자다.
- 링크를 아는 로그인 사용자는 누구나 이벤트를 조회하고 응답할 수 있다. 이벤트 ID는 UUID라 추측이 어렵다.
- 소셜 계정의 이메일이 기존 이메일 계정과 같으면 **같은 사용자로 자동 연결**된다(Supabase identity linking). 이때 기존 표시 이름을 유지한다. Kakao는 이메일 제공을 위해 비즈 앱 전환이 필요하다 (DB_SCHEMA.md 9-6).

## 5. 기능 명세

### 5.1 P0 (필수)

| ID   | 기능                     | 수용 기준                                                                                                                                 |
| ---- | ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- |
| F-01 | 회원가입/로그인          | 기존 `/auth/*` 흐름으로 가입·로그인·로그아웃이 동작한다. 가입 시 `profiles`가 생성된다.                                                   |
| F-02 | 이벤트 생성              | 제목·일시·장소는 필수, 설명·종료시각·정원·응답 마감시각은 선택이다. 생성자는 자동으로 주최자가 된다. 검증 실패 시 필드별 오류가 표시된다. |
| F-03 | 이벤트 상세              | 공지 내용, 일시, 장소, 주최자, 정원 대비 참석 인원이 표시된다.                                                                            |
| F-04 | 공유 링크                | 상세 화면에서 `/events/[id]` URL을 한 번에 복사할 수 있다. 복사 성공 피드백을 준다.                                                       |
| F-05 | 로그인 후 원래 링크 복귀 | 비로그인으로 이벤트 링크 접근 시 로그인 후 같은 이벤트 화면으로 복귀한다.                                                                 |
| F-06 | 참석 응답                | 참석/불참/미정을 선택·변경할 수 있다. 사용자당 이벤트별 응답은 1건이다.                                                                   |
| F-07 | 정원·대기자              | 정원이 가득 차면 새 "참석" 응답은 `waitlist`가 된다. 참석자가 불참으로 바꾸면 가장 먼저 대기한 사람이 자동 승격된다.                      |
| F-08 | 참여자 현황              | 참석/대기/미정/불참 목록이 이름과 함께 표시된다. 모두 열람 가능하다.                                                                      |
| F-09 | 이벤트 수정/삭제         | 주최자만 가능하다. 삭제 전 확인 대화상자를 보여준다.                                                                                      |

## 7. 데이터 모델 (초안)

> 확정 설계안(제약·인덱스·RLS·트리거·`respond_to_event` RPC·타임존 규약)은 [DB_SCHEMA.md](./DB_SCHEMA.md)를 따른다.

```sql
profiles (
  id          uuid primary key references auth.users on delete cascade,
  display_name text not null,
  avatar_url  text,
  created_at  timestamptz default now()
)

events (
  id            uuid primary key default gen_random_uuid(),
  host_id       uuid not null references profiles(id) on delete cascade,
  title         text not null,
  description   text,
  location      text not null,
  starts_at     timestamptz not null,
  ends_at       timestamptz,
  capacity      int check (capacity > 0),      -- null = 무제한
  rsvp_deadline timestamptz,
  created_at    timestamptz default now(),
  updated_at    timestamptz default now()
)

rsvps (
  id         uuid primary key default gen_random_uuid(),
  event_id   uuid not null references events(id) on delete cascade,
  user_id    uuid not null references profiles(id) on delete cascade,
  status     text not null check (status in ('going','not_going','maybe','waitlist')),
  created_at timestamptz default now(),
  updated_at timestamptz default now(),
  unique (event_id, user_id)
)
```

### RLS 정책

| 테이블   | SELECT        | INSERT                                 | UPDATE | DELETE |
| -------- | ------------- | -------------------------------------- | ------ | ------ |
| profiles | 로그인 사용자 | 본인                                   | 본인   | —      |
| events   | 로그인 사용자 | 로그인 사용자 (`host_id = auth.uid()`) | 주최자 | 주최자 |
| rsvps    | 로그인 사용자 | 본인                                   | 본인   | 본인   |

- 정원 판정과 대기자 승격은 **동시성 문제**가 있으므로 DB 함수(RPC) 또는 트리거로 트랜잭션 처리한다.
- 가입 시 `profiles` 자동 생성은 `auth.users` 트리거로 처리한다.
- 구현 시 `get_advisors`로 보안 점검을 하고, 타입은 `lib/supabase/database.types.ts`로 생성한다.

## 8. 비기능 요구사항

- **모바일 우선 반응형**: 360px 폭에서 모든 P0 기능이 가능해야 한다.
- **보안**: 모든 테이블에 RLS를 적용하고, 서버 측에서 권한을 재검증한다 (주최자 전용 동작).
- **인증 복귀**: `lib/supabase/proxy.ts`가 미인증 시 `/auth/login`으로 보낼 때 원래 경로를 `next` 파라미터로 보존한다. 로그인 성공 후 해당 경로로 이동하며, 오픈 리다이렉트 방지를 위해 내부 경로만 허용한다. (`createServerClient`와 `getClaims()` 사이에 코드를 추가하지 않는다.)
- **공유 링크 미리보기**: `/events/[id]`는 로그인이 필요하므로 카카오톡 등 링크 미리보기는 이벤트별 정보 없이 서비스 기본 카드(루트 메타데이터 + `opengraph-image`)로 표시한다. 이벤트 제목·일시를 미리보기에 노출하는 것은 MVP 범위 밖이다 (비로그인 공개 범위·RLS 결정 필요).
- **성능**: 상세 화면은 Server Component로 렌더링하고, 응답 변경은 Server Action으로 처리한다.
- **접근성**: 다크 모드 지원, 버튼·입력 요소의 키보드/스크린리더 접근성을 확보한다.

## 11. 리스크 및 오픈 이슈

| 구분        | 내용                                                             | 대응                                                             |
| ----------- | ---------------------------------------------------------------- | ---------------------------------------------------------------- |
| 진입장벽    | 참여자가 링크 클릭 후 로그인/가입을 해야 해 이탈할 수 있음       | 가입 폼 최소화, 인증 복귀 보장. 전환율이 낮으면 비회원 참여 검토 |
| 정원 동시성 | 동시 응답 시 정원 초과 가능                                      | DB 트랜잭션(RPC)으로 처리                                        |
| 대체 수단   | 카톡 투표·공지로도 어느 정도 해결 가능                           | 정원/대기자/현황 집계로 차별화                                   |
| 알림 부재   | 응답을 상기시킬 방법이 링크 공유뿐                               | 2차에서 알림 도입                                                |
| 오픈 이슈   | 수정 이력 전체 보관 여부, 주최자 공동 운영(공동 총무) 필요성     | 사용자 피드백 후 결정                                            |
| 기술 결정   | 폼 라이브러리(react-hook-form + zod) 도입 여부                   | 이벤트 폼 검증 요구가 있어 도입 권장                             |
| 스타터 정리 | `lib/supabase/proxy.ts`의 `/instruments` 공개 경로는 스타터 잔재 | 구현 시 제거                                                     |
